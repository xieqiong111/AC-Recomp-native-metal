# Native Metal implementation and acceptance

The Astral macOS target has one renderer: Metal. Its CMake source list excludes Vulkan replay/device/present and `vk_*` sources. It links Metal, QuartzCore, Foundation, MetalFX, SPIRV-Cross, SDL3 and opus. The builder and setup prerequisites no longer require Vulkan headers or MoltenVK. Other games' inactive upstream sources are not linked into this Astral target.

## Implementation

- Native command-list replay, draw and compute pipeline caches, vertex formats, render attachments, depth/stencil/blend/raster state and synchronized submit.
- GPU writes to shared storage buffers are completed before later CPU uniform/handle snapshots; this conservative synchronization favors correctness and can cost performance.
- Counter records use native shared-event handshakes: GPU reaches the report point, a serial CPU listener writes the existing 16-byte value/timestamp record, then an acknowledgement permits later GPU work. CPU snapshot preflights commit and wait for overlapping unpublished records before opening a draw/dispatch encoder. Pending records are bounded to 256 and verified published before successful command completion retires their resources. Ordinary guest CPU loads still require the existing NVN queue/fence protocol. The first batching version loaded the rescue save successfully but did not demonstrate a frame-rate gain. See [Apple event synchronization](https://developer.apple.com/documentation/metal/synchronizing-events-between-a-gpu-and-the-cpu).
- The streaming version submits each counter command buffer without blocking CPU encoding. Every new command buffer explicitly waits for the last submitted counter acknowledgement; the existing CPU-read, buffer-update, submit, present and explicit-wait boundaries still drain all submissions. At most 16 command buffers remain in flight; resources, counter records and completion serials retire only after the whole batch succeeds. Uncompleted submissions use their remaining two-second deadline measured after commit returns; already-completed records are polled first. Timing labels now use `drain-wait` for actual blocking during a later drain, attributed to each buffer's submission reason; this differs from the old commit-to-completion wall interval. Summed GPU command-buffer intervals are not a GPU busy-time measurement when submissions overlap. This version has built, passed focused read-only review, been signed and loaded the rescue save after user-approved restart. A 47-second observation showed 39.8 fps median (20.9–43.8); the preceding batching observation was 38.8 fps median with different draw counts, so no controlled gain or sustained 60 fps is established.
- Dynamic uniform snapshots and uncached host-derived bindings reuse exact-size shared Metal buffers after GPU completion. Each new snapshot copies current bytes and clears only the remaining padding; the ready pool retains at most 64 MiB. This reduces per-draw allocations while preserving independent descriptor bounds and existing synchronization.
- Inline uniform versioning defers inline uniform updates within one replay submission. It owns each update's bytes (at most 64 records / 256 KiB); independent read-only uniform snapshots overlay these updates in command order onto their copied prefix. Older snapshots and zero padding remain unchanged. Direct storage, vertex, index, indirect and texture accesses materialize overlapping updates before creating their encoder; virtual or unknown texture backing flushes conservatively. Every counter marker and submission end materializes all remaining updates after draining GPU work. Oversized updates retain the synchronous path. Physical host ranges resolve NVN virtual mappings to their backing pool; the current kernel's MapMemory copies rather than introducing distinct host virtual aliases. Lifecycle operations still drain the replay worker. This is an original implementation informed by the uniform-version dependency model in [MacNativeGames](https://github.com/ly05010419/MacNativeGames/blob/ad2b6f04701b1478a7c17e1f6319a1d86f5c75f9/games/totk/third_party/d2r_gfx/gfx/nvn/nvn_mtl.m), without its Metal 4 alias APIs or GPU-copy path. Ordinary unfenced guest CPU reads during replay remain outside the synchronization contract. Candidate build, review and runtime acceptance are recorded separately; no performance gain is established.
- Each completed snapshot retains its last copied prefix length. Fresh allocations clear their full suffix; reuse clears only the former prefix bytes exposed by shrinking, while growth or equal-length reuse preserves the existing zero suffix. These pooled bindings are read-only; writable storage buffers use a separate guest-memory path. Any future GPU write into a pooled snapshot must invalidate this invariant before reuse. Dynamic prefixes still copy every use, with no change to the 64 MiB cap or completion barrier.
- Host-derived support and driver bindings reuse immutable snapshots within a completed command-buffer lifetime (up to 32 values of each kind, copying on overflow). Support keys retain viewport float bits; driver keys cover stage and all relevant storage/uniform address/size pairs. Shader constants have independent read-only buffers keyed by the process-lifetime ShaderInfo. Dynamic guest uniforms still snapshot on every use.
- Persistent Metal buffers alias NVN memory pools. Texture upload handles tiling, levels, arrays, compressed formats and views with explicit unsupported-operation failures.
- Existing shader translation produces offline SPIR-V. Pinned SPIRV-Cross compiles to MSL; Metal builds native shader functions and pipelines.
- Fragment alpha comparison/reference values are recorded and specialized into real shader discard; RGB/RGBX/R11 formats retain logical alpha=1 when sampled or blended.
- Scissored/masked clears use a native clear pipeline preserving unaffected pixels/channels. Native MetalFX Spatial and CAMetalLayer handle presentation and the performance overlay.
- Known sampled cube/non-cube backing incompatibility follows the prior sampled-image contract using an explicitly initialized, scalar-type-correct six-face texture; unsupported storage/attachment/range cases still fail.
- Depth bounds use native `setDepthTestMinBound:maxBound:` on macOS 26+ Apple10 GPUs, validating/clamping normalized bounds and resetting the state when disabled. Other hardware fails explicitly for nontrivial bounds. See [Apple API](https://developer.apple.com/documentation/metal/mtlrendercommandencoder/setdepthtestminbound:maxbound:?language=objc).
- CPU recompilation, services, SDL input/audio, language/font loading and save paths are retained.

## Dedicated replay worker

A separate prepared-bindings candidate keeps the first preparation's command-local `StageImages` descriptor values and immutable sampler references. After all stages and attachments have warmed their usage, it calls `refresh_stage_images` to materialize every texture again and retain final views. Both texture passes and the attachment order remain; dirty uploads, concurrent WriteTexels, uniform/counter texture guards and backing upgrades still execute before creating the encoder. Dynamic buffer snapshots remain at bind time. This removes the second descriptor/handle/sampler resolution and duplicate buffer preflight without a persistent cache or backing-generation shortcut. The candidate has built, been signed and passed focused read-only review. After user-approved save/restart it was installed, passed full app signature verification and initialized native Metal/MetalFX with real draw commands. Rescue loading, rendering correctness and performance acceptance remain pending.

The native target queues Metal replay on a dedicated host thread. This allows game logic and command recording to overlap replay and GPU completion waits on separate CPU cores; it does not automatically parallelize a single game function. Other targets retain their previous worker policy.

Each submission owns its complete called-list graph and deferred binding arrays before returning. Queue operations and lifecycle barriers share an enqueue-order boundary; destructive program, descriptor-pool and memory-pool changes drain prior work without holding that boundary while waiting. Texture image ownership is exchanged under the object lock. Guest buffer contents retain the NVN synchronization contract: the game must wait for the appropriate fence before overwriting or freeing submitted memory.

Presentation resolves the last submitted frame's object epoch without advancing the reclamation floor. Only submission replay advances that floor. Legacy in-place texture publication and replay-time epoch override are disabled for this native target. GPU completion is still awaited on the replay worker, preserving buffer recycling and write-back ordering.

The worker revision has built, passed focused read-only review, been signed and run into the Chinese FILE 01 rescue scene. A five-second sample shows Metal submission on the named `nvn replay` thread; game command recording runs separately. One thread CPU snapshot attributed 23.8% of one core to the worker. This proves actual work moved onto the dedicated thread, not a frame-rate gain. Sequential observations differed in draws per presentation (about 1084 versus 1402), so their frame rates are not a controlled comparison. Sustained 60 fps remains unproven.

## Evidence and remaining acceptance

Both 30 and 60 fps arm64 executables compile and link. The compile commands exclude Vulkan renderer sources; `otool -L` contains Metal/MetalFX and no Vulkan/MoltenVK dependency. Native Apple M5 device initialization and MetalFX presentation have run with actual game frames. Actual native execution has reached the animated 3D title, Chinese menus, save selection and a loaded FILE 01 character-creation scene. The user confirmed Z+C input and normal Chinese menu text. CUA separately observed the 3D character models, clothing and lighting. The session exited normally with code 0 after window quit; no Metal fatal was recorded in this successful session. A subsequent run reached FILE 01 dialogue and the motorcycle combat tutorial after fixing sampled cube compatibility and native depth bounds. CUA observed the moving road, motorcycle, enemies, effects and Chinese guide. The user physically verified that C (ZR) shooting and directional movement both work. This establishes early interactive combat only, not a completed chapter or whole-game rendering correctness.

The native implementation retains explicit failure points for unsupported commands/formats. Current limitations include nontrivial depth bounds on pre-Apple10 hardware, unsupported alpha-output layouts and logic operations, some primitive expansion/copy/3D texture paths and masked integer clears. These are compatibility boundaries to implement when exercised, not success stubs. No claim of complete GPU semantics is made.

No unit-test suite was run for this work, per the current user instruction. Builds, source composition checks and actual device execution are separate evidence. Old renderer gameplay results do not substitute for native Metal acceptance.

In the observed M5 session, title-screen intervals varied around 44–60 fps and character creation around 20–30 fps. This is an experimental 60 fps game-code mode, not sustained 60 fps performance. Motorcycle combat samples before snapshot pooling were roughly 17–23 fps. A later baseline run also reached the FILE 01 rescue scene; this does not establish chapter completion.

The first performance change reuses completed snapshot buffers. On the actual title screen, allocations stopped at 544 while reuse exceeded one million, with 1508 KiB retained. A 5-second CPU sample no longer showed the repeated snapshot buffer initialization stacks seen in the baseline; GPU completion waits remained prominent. For the same title draw-count window (30,000–100,000 draws, 16 logged intervals each), median presentation rate was 56.55 fps before and 59.0 fps after. These short sequential observations can be affected by scheduling and thermal state; they do not establish combat performance or sustained 60 fps. Both executables were rebuilt, signed and the optimized app was launched with 1920×1080 MetalFX output to the actual display.

The copy implementation additionally avoids clearing the source prefix immediately before copying over it. This incremental change has built, passed focused source review, been installed after the user saved, and run through Chinese menus and save loading into the FILE 01 rescue scene. Previous app binaries were preserved. Observed rescue intervals were mostly around 30–32 fps, with 18–20 fps low intervals also recorded. A 5-second sample showed no repeated snapshot buffer initialization stacks, with 2.7 GB physical footprint (2.8 GB peak). No new runtime failure was recorded during this observation. These are uncontrolled sequential observations, not a paired fixed-camera benchmark or proof of sustained 60 fps.

The current 36-patch composition includes lower-address planning, 24 region-order candidates and region-membership pointer classification. QueryMemory sorts its two free regions before marking their complement inaccessible. It has built and started successfully, but starts can still fail if no contiguous 16 GiB alias block is available. The observed successful start used alias before stack; stack-before-alias still needs runtime acceptance. No region was shrunk and no occupied host mapping was overwritten. The active app retains its original bundle identity for normal window/tool recognition.

The host-binding reuse build has compiled, passed focused read-only source review, been signed and installed after the user saved. The user confirmed entering the rescue scene. All three cache counters increased in actual gameplay: support 101,687, driver 74,977, shader constants 1,077,334, with 453,362 KiB of source copying avoided at one observation and 1 KiB of persistent shader constant buffers. Title-screen support/driver reuse had been zero, illustrating why scene-specific evidence matters. Dynamic guest snapshots and GPU synchronization remain unchanged; these counters do not establish a controlled frame-rate improvement.

The uniform-versioning build was installed after the user saved and approved restarting, and the user confirmed loading the original rescue save. A 42-second observation recorded 18.35 fps median (17.4-19.7), about 1382 draws/present, with no runtime fatal. The immediately preceding streaming log tail had already fallen to 17.4 fps median at similar draw counts; the older 39.8 fps observation is not a paired baseline. A separate Steam/Wine process was observed at about 173% CPU. These are confounders, not proof of causation or a controlled gain/regression. Per 600 presents, all 600 inline updates totaled 19,200 bytes, with 600 submit-boundary flushes and 19,200 overlay bytes; no capacity, overlap or counter-marker flush occurred. One complete textual timing group appeared within the FPS capture but crosses the collection start, so there is no full 600-present group wholly inside that window. Later timing groups and a five-second thread sample are separate diagnostic evidence, not a paired benchmark. Stable 60 fps remains unmet.

The latest scheduling candidate restores the streaming renderer source snapshot and explicitly requests `QOS_CLASS_USER_INTERACTIVE` for the macOS event-loop thread and native Metal replay worker. The existing game-thread entry already makes that request; the replay worker uses `std::thread` and previously bypassed it. Each new request logs its return code and the requested QoS readback. This is a scheduling hint, not CPU affinity, effective-priority measurement or guaranteed performance-core placement. No App Nap, real-time or global system policy changes are included.

The candidate's four renderer source files match the saved streaming snapshot byte-for-byte; only the event-loop and replay-worker source files receive QoS additions. The previous uniform/prepared-binding sources remain backed up. Historical streaming binaries do not have a complete source-input receipt, so this does not establish their full source provenance. Both candidate arm64 targets built and passed signature verification, canonical recomposition and read-only source review. The candidate is installed; main and replay QoS requests returned success and read back USER_INTERACTIVE. A cold restart of the preserved streaming binary recorded 18.05 fps median; a subsequent standard macOS application launch recorded 16.0 fps median. Neither restored the historical 39.8 fps observation, and neither is a fully paired performance comparison.

Power inspection subsequently found 7% battery charge and an adapter reporting only 8 W. The installed QoS build recorded 17.9 fps median over 600 rescue presents under that condition. After the user changed to a direct 65 W supply, the same process and binaries recorded 40.0 fps median (33.4-41.9), with comparable draw counts and no runtime errors observed. A separate three-second CPU trace then placed 973 of 978 replay samples on performance cores; main-event-loop samples also included performance cores. This strongly supports inadequate external power as a major contributor to the low-frame-rate episode. It does not prove QoS-specific benefit, fixed core affinity, a battery threshold or sole causation. Sustained 60 fps remains unmet.

## counter 快速路径与统计（2026-10-24）

全部 counter 类型的 ReportCounter 默认不再在命令流中等待 CPU 回调：临时 host 时间戳在编码期写入 guest 记录，对应提交完成后由 drain 用该提交的 GPUEndTime 回填（带单调下限保护），随后才置 published。记录值与旧实现完全一致（{sequence, host ns}，kind 无关），`NX_COUNTER_LEGACY=1` 可整进程回退到原 shared-event 通知 + ack 等待链。依据：Astral Chain 在 fence 等待之后才读 counter（Puddz/AstralChain-PC 一手注释），记录在编码后永不为空；首轮实测确认本作 9.5 次/帧全部为 kind 1（SAMPLES_PASSED），其记录不含 GPU 计算数据，编码期发布不改变值语义。

新增诊断（每 600 present 一行 `nvn/metal counter-stats`）：counter kind 直方图、快速路径 GPU 回填/临时值计数、legacy 回调延迟（avg/max）、CPU-read 强制 drain 按站点计数（draw/dispatch/clear/copy）。不输出任何裸地址。

### counter 不再拆分 command buffer（2026-10-24 下午）

快速路径默认不再在 counter 处调用 end_encoding/submit 拆分 command buffer（Apple TBDR 上 mid-pass 拆分意味着附件写回+重载，每帧 9 次的纯带宽开销）；counter 记录挂到下一个自然提交，drain 用该提交的 GPUEndTime 回填。`NX_COUNTER_SPLIT=1` 恢复"快速路径+拆分"的历史行为用于归因对照，`NX_COUNTER_LEGACY=1` 仍为完整旧链。同一自然提交内的多个 counter 获得相同 GPUEndTime（时间戳粒度变粗，帧内差分只会偏小不会偏大，不会触发游戏的降帧 governor）。drain 起始处新增 awaiting 扫描：没有后续提交的 counter 以临时值发布，避免空 drain 误报。counter-stats 行新增 split-drain 段（counter 发生时 render encoder 是否打开、counter 间隔 draw 数 avg/max）。

### cpu-read 与 uniform 更新跳过 present 完成等待（2026-10-24 傍晚）

present 的 command buffer 只访问 drawable 与内部 upscale/HUD 纹理，从不读写 guest 内存，因此 CpuRead 与 BufferUpdate 两类 commit_wait 不再等待 present 提交完成（显示截止时间），让下一帧编码与显示等待重叠；被跳过的 present 提交保留在队列中，由下一次完整 drain（present/submit/counter/explicit-wait）退休。counter 回填改为在每个提交完成校验后内联执行；存在延迟提交时跳过严格 published 检查、counter 退休与快照回收（延迟提交仍持有各自 counter 与快照缓冲）。FIFO 语义下新提交的 GPU 执行仍在 present 之后，本改动只解除 CPU 编码侧的串行化。

### UpdateUniformBuffer 范围化等待（2026-10-24 晚）

present 本身同步等待自己的 command buffer，队列中不会有残留 present 提交，因此上一节 present-defer 对本作是无效路径（保留，无害）。实测 UpdateUniformBuffer 的整队 drain 等的是当前帧已提交游戏 CB（约5ms真实GPU工作）。由于 uniform 绑定在 bind 时做快照拷贝（snapshot_guest_buffer），零拷贝 alias 只覆盖 storage/vertex/index 等缓冲：buffer_for_gpu 现按 canonical host 区间记录"自上次完整 drain 以来 pending/开放 CB 引用过的 alias 区间"（合并区间表，完整 drain 时清空；uniform 更新自身的解析不记录）。UpdateUniformBuffer 仅当更新区间与该表重叠时才 drain（重叠时行为与旧版完全一致），否则直接写入。counter-stats 新增 buf-update waits/skips 计数。

### GPU trace 定位与 encoder/CB 标签（2026-10-24 晚）

3秒Metal System Trace（performance-gpu-20261024-rescue.trace，与FPS窗口分开）：GPU busy占区间82.4%（fragment 78.2%、vertex 54.3%重叠、compute可忽略），按42.35fps折算约19.5ms/帧真实GPU工作，距60fps预算需削减约3ms。fragment区间约67个/帧，中位0.033ms（微小pass尾约2ms/帧），最大单区间中位2.4ms、p90 7.9ms。shader profiler表为空（此配置不可用）。为下一轮按名归属，所有render/compute/blit encoder与command buffer（按提交原因）现在设置标签（render-WxH-cN±depth、present-final、metalfx-input-copy、hud、copy-tex、compute-dispatch、cb原因名）；标签不影响执行。

### GPU 写区间跟踪与精确 cpu-read（2026-10-24 晚）

带标签trace按名归属（performance-gpu-labels-20261024.trace）：主场景pass render-1920x1080-c4+depth 每帧打开约9.1次、fragment合计约5.5ms/帧；MetalFX Scale+Sharpen+input-copy合计约2.5ms/帧（用户要求保留）；1080p无深度pass约1.2ms；mip链各pass合计<1ms。主pass的重复打开部分来自cpu-read/submit/present强制drain的end_encoding（每次1080p×4目标+深度的TBDR写回+重载）。据此实施：写storage绑定的draw/dispatch把写入区间记入合并区间表g_gpu_write_intervals（完整drain清空）；draw/dispatch移除整队prepare_cpu_reads，uniform快照预检（metal_shader.mm）与U8索引拷贝改为prepare_write_read(bytes,len)——仅与GPU写区间重叠时drain（重叠时行为与旧版一致）。clear/copy保持原保守整队检查。counter-stats新增write-read drains/skips。

### clear 站点保守 drain 移除（2026-10-24 深夜）

metal_clear.inc 经核查不读任何 guest 内存（无 contents/memcpy/映射访问），clear() 的整队 prepare_cpu_reads 为纯保守残留，已移除（copy 站点保持，实测恒为 0）。至此 draw/dispatch/clear 的整队 cpu-read 全部消除或精确化。GPU counter 表（gpu-counter-value/metal-gpu-counter-intervals）在此配置的 Metal System Trace 中为空且无 GPU Counters 模板，shader 级热点剖析需后续在代码内加 MTLCounterSampleBuffer 采样候选。

### MTLCounterSampleBuffer 逐 encoder GPU 采样（2026-10-24 深夜）

NX_GPU_COUNTERS=1 时启用：每个 render encoder 关闭处经 blit encoder 采 stage-boundary GPU 时间戳（withBarrier），提交时 resolve 到共享缓冲，每 600 presents 输出一行 gpu-encoder-ms（按 encoder 标签聚合的逐 encoder GPU 毫秒与次数，仅统计同一 command buffer 内相邻采样差）。用于剖析主 pass 7.3ms 的内部构成。经典 API 采样点为 MTLCounterSamplingPointAtBlitBoundary；默认关闭不影响正常运行。

### early-Z 探索结论与按管线绘制直方图（2026-10-24 深夜）

earlyFragmentTests属性在本SDK（macOS 27/Metal 4时代）已从MTLRenderPipelineDescriptor移除且无替代名——Apple Silicon的TBDR由驱动按MSL自动推断early-Z（不discard不写深度的shader自动受益），该杠杆不存在，探索代码已回退。替代实施pso-stats：每draw按管线对象记录draw数与索引数（经典API无逐draw GPU时间，此为shader负载代理），每600呈现输出按索引数排序的top-8（pso指针/draw数/索引数），供下会话定位最重翻译shader并做MSL特化。
